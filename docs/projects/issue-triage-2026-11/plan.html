Order of work

PR 1 — #21 and #17: one creation per singleton

  • P1a. getSync: if a creation is already in flight for the token, throw a retriable AsyncOnlyBinding without running the creator again (packages/core/src/index.ts:1384).
  • P1b. registerResolution: write the cache only if this creation is still the current one (resolutions.get(sym) === updated) and nothing is cached yet; delete the in-flight entry only on the same identity check (index.ts:1275).
  • P1c. Tests: the issue's cases 1, 2a, 2b; a React mount test that counts creations (one reader, two readers in one Suspense, StrictMode — all must be 1); #17's re-apply-while-in-flight test in the P6 block of singleton-cache.test.ts.

Open question: what does the caller of a creation that started before unbind receive? See Q1.

PR 2 — #18: say what the adapter does, and make it safe to upgrade

  • P2a. Decide whether the adapter keeps a cached value on re-apply like core, or keeps rebuilding (Q3). Either way, add a test that pins it and a README line.
  • P2b. Un-awaited adapter.bind() on a bound token registers late, because it awaits unbind first. If Inversify 7 offers a synchronous unbind, use it; otherwise document that bind must be awaited. (To check against the installed Inversify.)
  • P2c. One line in core's apply TSDoc: an override that changes scope (singleton → transient) does not reuse the cached value. Confirmed in code: get reads the new binding's scope.
  • P2d. Add a release checklist to MAINTAINING.md: core, react and inversify release together, because the adapter depends on core via workspace:* (an exact pin once published). Open PR #23 (npm publishing workflow) should follow it.

PR 3 — #20: each concurrent branch keeps its own chain

  • P3a. False cycle. Today one CircularDependencyMonitor with one mutable stack serves a whole request, so siblings resolved with Promise.all see each other. Each get should hand its creator a child context carrying its own, immutable chain. That also removes the remove() bug that pops the wrong entry and garbles the printed path (index.ts:865).
  • P3b. Hang. Before awaiting another request's in-flight creation (index.ts:1348), walk a container-level wait-for map (creation → the creations it is awaiting). If the walk reaches the caller's own chain, throw CircularDependency instead of waiting.
  • P3c. API. ResolutionRequestMonitor and resolutionRequestMonitorFactory are public, and their shape assumes one stack per request. Changing that is a breaking change for custom monitors, hence 0.2.0.
  • P3d. Tests: both repros; the printed path for a real cycle under concurrency; no regression in the existing per-request isolation tests.

Open question: how to carry the chain. See Q2.
