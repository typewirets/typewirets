Extend the prototype: one workflow stages, waits for approval and tags, and a plan step makes every release resumable

Key: npm-releaseDate: 2026-11-07Author: Claude Code, with the maintainerStatus: A1 built; the maintainer said "go ahead and implement" on 2026-11-07Source: product.html (approved 2026-11-07), the prototype at 90b8ee6, npm's docs and CLI source

Keep the prototype's shape (one workflow that stages, waits and tags) and add a plan step that reads npm, git and the changelogs before anything is staged. It delivers B1–B16 with the fewest moving parts, and one rule covers every recovery: run the same version again on the same commit.

Approaches

A1. One workflow, plus a plan step Picked

Plan (npm, tags, changelogs, provenance) → stage → poll the registry until live → tag and release.

  • Effort S: extends the prototype.
  • Risk: a waiting job holds a runner for up to 3 hours; free on a public repo.
  • Recovery: re-run failed jobs, or run the same version again.

A2. Two workflows

"Stage" ends after staging; a separate "Finish" (dispatched by hand, or on a schedule) tags once all are live.

  • Effort M.
  • No runner waits, but every release needs a second click or a cron.
  • Twice the trusted-publisher surface to reason about.

A3. A release tool (semantic-release, changesets)

Let a tool pick versions, write changelogs and publish.

  • Effort M–L.
  • Adds npm dependencies to CI (AGENTS.md: a reason and a named sign-off).
  • They commit back to main by default, against M2; staged publishing support is unconfirmed.

R1. A1. It already exists, keeps one place to look, and its plan step turns every recovery into "run it again": B13 and B15 then need no separate path.

Shape

Bounds and latitude

  • N1. AGENTS.md holds: SHA-pinned actions from GitHub only, top-level contents: read, no persisted credentials, pnpm from the pinned Corepack, no new dependencies.
  • N2. Node 22 and Corepack stay as in ci.yml; PR #19 (Node 24, pnpm 12) is separate.
  • N3. Not now: a version suggested from commits (Q2 B), a release skill, publishing to registries other than npm.
  • L1. The builder decides the script's structure and the wording of summaries. It checks first before adding any action or dependency, or widening permissions.
  • L2. Done comes in two stages (Q3 A): this PR is mergeable with every testable line covered, then, after merging, the next real release (likely 0.2.0) ships end to end. A workflow can only be dispatched from main, so stage 2 needs the merge.

Agent's calls

  • C1. A finishing run must be on the commit the live packages were built from, read from their npm provenance. Otherwise B10 would tag the wrong commit, and B15 would build adapters from different code than their core.
  • C2. "Higher than npm's latest" compares against the highest version a package has, pre-releases included, so 0.2.0-rc.1 after 0.2.0-rc.2 is refused.
  • C3. The provenance check after release warns and never fails: by then the packages are live, and the tag and release should still follow.
  • C4. The rules live in exported functions tested with node:test, so the tests need no new dependency.
