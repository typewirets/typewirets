The maintainer ships every typewirets release from GitHub, and nothing goes live without their own 2FA

Key: npm-releaseDate: 2026-11-07Author: Claude Code, with the maintainerStatus: draft, awaiting approvalSource: the maintainer's answers in chat, 2026-10-23 to 2026-11-07

One run on GitHub releases all three typewirets packages at one version. The maintainer approves each package on npm with their own 2FA, and only then do the git tag and GitHub release appear. No npm token is stored anywhere. The behaviour below delivers that.

Value

  • V0. For the typewirets maintainer: release @typewirets/core, @typewirets/inversify and @typewirets/react from GitHub in one repeatable run instead of by hand from a laptop. The maintainer's own 2FA approval on npm is the only gate, and npm, the git tags and GitHub releases always agree.
  • V1. The same steps every release, with no laptop setup or remembered commands. The maintainer: "automatically publish with GitHub Actions with the manual deployment… create GitHub tags and all that."
  • V2. Nothing reaches npm users without the maintainer's 2FA, even if GitHub, CI or a dependency of the build is compromised. The maintainer chose staged approval on 2026-10-26.
  • V3. No long-lived npm token to leak or rotate, and the flow keeps working after npm ends direct publishing with tokens in January 2027.
  • V4. A tag or GitHub release never exists for a version that isn't installable from npm. Proposed by the agent; see Q1.
  • V5. Anyone can check which commit of this repository a published version was built from.

One release, start to finish

Behaviour

GroupWhat happens
StartB1. The maintainer starts a release from GitHub by giving one version number, and all three packages are released at that version. Q2: the maintainer types it.
StartB2. A dry run is the default. It checks and packages the release the same way a real run does, and nothing changes on npm, in git tags or in GitHub releases.
GuardB3. A release refuses to start, and says why, when the version isn't valid, a package's changelog has no section for it, the version is already on npm, its tag already exists, or a real (not dry) run isn't from main.
GuardB4. Every package as shipped carries the release version and depends on @typewirets/core at exactly that version. The packages ship together (MAINTAINING.md, Release Checklist).
StageB5. A real run puts all three packages on npm awaiting approval, and none can be installed yet.
StageB6. The run tells the maintainer what to approve: one entry per package, @typewirets/core first.
StageB7. No npm token is stored in GitHub or anywhere else. Releases keep working with every package set to "require 2FA and disallow tokens" on npm.
ApproveB8. A package becomes installable only after the maintainer approves it on npm with 2FA, on npmjs.com or from a terminal.
ApproveB9. A pre-release such as 0.2.0-rc.1 installs only when asked for by its version or the next tag. A plain npm install @typewirets/core keeps getting the latest stable version.
FinishB10. Once all three packages are installable, the v<version> tag, on the commit the release was built from, and the GitHub release appear with no further action. Q1: only after all are live.
FinishB11. The GitHub release notes are each package's changelog section for that version, and a pre-release is marked as one.
FinishB12. Each published version shows provenance that names this repository and the release's commit.
RecoverB13. If the maintainer approves after the run has stopped waiting, they resume the same release. It then creates the tag and GitHub release, and stages nothing again.
RecoverB14. If the maintainer rejects a staged package or abandons the release, no tag and no GitHub release are created.
Whether a rejected version number can be staged again is for the design brief to confirm.

How it's built (workflow shape, how the run waits, tools) and the bounds are in the design brief, which comes after this one is approved.
