#20 is still open, and preload now hangs on a cycle

Date: 2026-11-09Author: Claude Code (Opus 5.5)Status: superseded by product.html and design.html (2026-11-09)Source: issue #20, core at 0337a79

Issue #20 is not fixed. Both of its bugs still reproduce on main. Since 0.2.0, container.preload() hangs forever on any dependency cycle, so the bug can now be hit through a public API. The fix agreed on 2026-11-05 (triage plan, PR 3) still holds. What has changed is the release: 0.2.0 already shipped without it, so the fix goes out as 0.3.0.

What causes each bug?

BugCause in code
False cycle (C1)Each top-level request gets one CircularDependencyMonitor, and all of that request's branches share its mutable set and stack (index.ts:836–882). remove() pops whatever entry is on top of the stack, not its own, which is why the printed path is garbled.
Hang (C2, C3)get awaits any in-flight creation it finds, without checking first whether that creation is itself waiting on the caller (index.ts:1387–1391).

How do we fix it?

One core PR. Steps S1 to S3 are the triage plan's P3a to P3c, updated for today's code.

  1. S1. One chain per step. Each get and getSync gives its creator a child context that holds an immutable chain: the parent's chain plus the type being created. The cycle check becomes "is this type already in my chain?". Siblings started with Promise.all or getAllInstances(ctx) each get their own chain, so the false cycle and the garbled path both go away. The chain is passed explicitly, not through AsyncLocalStorage, so it works in browsers too. That was decided in triage Q2.
  2. S2. Check for a wait cycle before joining. ResolutionState keeps a wait-for map: for each in-flight singleton creation, the creations it is currently waiting on. An edge is added when a step inside a creation joins or starts another creation, and removed when that creation settles. Before joining an in-flight creation, get follows the map from it. If the walk reaches a creation in the caller's own chain, get throws CircularDependency with the full path instead of waiting. When it throws, both requests reject and nothing is left cached, so a retry runs cleanly. The Go port's waitCycleLocked and typewirepy#15 (finding 5) work the same way.
  3. S3. Monitor API. Today the pluggable ResolutionRequestMonitor does the cycle detection, and its shape assumes one stack per request. The wait-for check needs state that spans the whole container, so it has to live in core. Where cycle detection lives is the open choice; see Q1.
  4. S4. Behaviour tests (packages/core/src/__tests__/). Each test fails on today's main:
    • C1 resolves to reader(client) + writer(client), and Client's creator runs exactly once.
    • C2: both gets reject with CircularDependency well within 1 second, and each path ends in a repeated type.
    • C3: preload() rejects with CircularDependency, and a non-cyclic preload() on the same container still works.
    • A real cycle inside one branch of a Promise.all reports a clean path, with none of its siblings' types in it.
    • The existing tests for per-request isolation, singleton creation and preload pass unchanged. The React and Inversify suites also pass.
  5. S5. Release. Changelog entries for core, react and inversify, plus a README note on concurrent resolution. The version follows the release checklist and Q2.

What could go wrong?

Your answer

Q1. Where should cycle detection live?

Cycle detection always runs, even with a custom monitor. The monitor gets the step's path as an extra argument, so existing implementations still type-check. A custom monitor can no longer switch cycle detection off.

Fewer moving parts in the API, but detection is split in two: chain cycles in the monitor, wait cycles in core. A custom monitor that ignores the path still has today's bugs.

Q2. Which release?

Before 1.0, a minor version is where behaviour changes go, and this one changes what custom monitors do.
