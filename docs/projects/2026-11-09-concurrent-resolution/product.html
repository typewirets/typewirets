A cycle fails the same way however you resolve, and never hangs

Key: concurrent-resolutionDate: 2026-11-09Author: Claude Code (Opus 5.5), with the maintainerStatus: product brief, awaiting approvalSource: issue #20 and the maintainer's answers in chat

A developer gets the same answer from the container whether it resolves one thing at a time or many at once. A graph without a cycle always resolves. A graph with a cycle always fails with the same readable CircularDependency error, and never hangs. Their own monitor can still see every step and decide how errors are handled.

Value

V0. Developers who build apps on typewirets can resolve concurrently (with preload(), or Promise.all inside a creator) and get exactly what they would get resolving one thing at a time. A wiring mistake shows up as a clear error they can act on, and they keep control over how resolution errors are handled.

  • V1. Switching to preload() or parallel resolves never changes whether an app's graph works.
  • V2. A cycle fails a unit test, rather than leaving app startup waiting forever.
  • V3. The error reads the same every time, so developers learn it once.
  • V4. Teams keep their own error handling: reporting, custom errors and fallbacks.
  • V5. The TypeScript port meets the three concurrency expectations of the typewire contract it shares with the Python and Go ports: each resolve keeps its own chain (B1, B8), concurrent first resolves of a singleton share one creation (B2), and a cycle that runs through another resolve's in-flight creation raises an error instead of hanging (B3, B4).

Terms used below

RequestOne top-level call: get, getSync, or a wire's getInstance / getInstanceSync on the container. preload() makes one request per singleton it creates.
StepOne resolve of one type inside a request, made by the request itself or by a creator through its ctx. A step can hit the cache, join a creation already in flight, or run a creator.
ChainThe types a step sits inside, from the request's type down to the step's own type.
CycleCreating a type needs that same type before the creation finishes. This happens directly (A needs A), through the step's own chain, or by waiting on an in-flight creation that is itself waiting, directly or through others, on the waiting step's chain. It applies to every scope: singletons, and bindings with any other scope, which today behave as transients. Not a cycle: waiting on an in-flight creation that isn't waiting back, or a resolve a creator makes after it has returned its value (that is a new request).

Behaviour

Resolve concurrently

B1A creator that resolves several imports at once, with Promise.all or a wire group's getAllInstances(ctx) (a group made with typeWireGroupOf), receives every value, in the order requested, when the graph has no cycle. Example from #20: App resolves Reader and Writer, both of which import Client. The result is reader(client) + writer(client), not an error.
B2Concurrent first requests for the same singleton share one creation: its creator runs once, and every requester receives the same instance. If that creation fails, every requester receives the same error, nothing is cached, and the next request runs the creator again. Transient types are never shared: each step runs its own creator, as today.

Cycles fail the same way

B3A cycle fails with CircularDependency however it is reached. get and getInstance reject, whether called once, from Promise.all inside a creator, as concurrent top-level requests, or through preload(). getSync and getInstanceSync throw synchronously. Unchanged: getSync still throws AsyncOnlyBinding when it meets an async creator, or a singleton whose creation is still in flight.
B4Every request caught in a cycle settles with a CircularDependency error as soon as the creators it waits on outside the cycle have settled. No timer is involved, and none stays pending. Today, get(A) and get(B) started together on an A ⇄ B cycle never settle. A creator that never settles on its own is out of scope.
B5No value is cached for a type whose creation rejected because of a cycle: the cycle's own types, and the types above them in the failing chains. Once the developer breaks the cycle by re-applying a wire (wire.apply(container), or wire.withCreator(…).apply(container)), the same container runs the new creator on the next request. A creator that catches the error and returns a value has that value cached as usual. Singletons outside the cycle that are created by the same preload() are still cached, as preload does today.
B6await container.preload() in a test rejects with CircularDependency when a bound singleton's creation runs into a cycle, so CI catches it. As today, if several creations fail, preload rejects with the first error to arrive and lets the others finish.

The error reads the same

B7The error message keeps today's four lines. Failed To Resolve names the repeated type. Resolution Path starts at the request's type and ends with the repeated type in brackets, and that type also appears earlier in the path. numberOfPathsToPrint shortens long paths as it does today. 
Failed To Resolve A
Reason: CircularDependency
Instruction: Check for circular references in your dependency graph and refactor to break the cycle.
Resolution Path: App -> A -> B -> [A]
A request that starts at A shows A -> B -> [A].
B8Every CircularDependency path names each type of the cycle, in order, ending with the repeated type in brackets. Before the cycle, the path shows only the failing request's own chain. It never includes a type that is neither on that chain nor part of the cycle, such as a sibling branch's type. When the cycle runs through another request's in-flight creation, its types appear in the path, because they are part of the cycle. When two requests are caught in one cycle, each one's error shows the whole cycle. Whether both errors carry identical text is left to the design. Today, sibling branches leak into each other's path (App -> Reader -> Client -> Writer -> [Client]); under B1 that example has no error at all.

Monitors see and adapt

B9The cycle check runs for every step, whether or not a custom monitor is configured. A monitor can't skip the check, and it always receives the CircularDependency error the check raises. What happens next is the monitor's choice (B11).
B10A custom monitor is called for every step of every request, including cache hits and joins of an in-flight creation. Each call gets the step's type, its chain, and its result or error. Steps running at the same time each report their own chain. A step is reported as started before the steps nested inside it, but sibling steps come in no fixed order.
B11A custom monitor can change a step's outcome, synchronously or asynchronously. It can throw a different error in place of any error, or return a value in place of any error other than CircularDependency. The step's caller receives what the monitor gave. Example: report a CircularDependency to an error tracker, then rethrow it, or throw the team's own error type. A value a monitor returns is never cached as that step's own type. It does go to whatever was waiting on the step, and that creation may succeed and be cached.
B12A cycle always ends in an error for its callers. If a monitor returns a value for a CircularDependency, the step's caller still receives an error, and nothing waiting on that step is created or cached with the returned value. Why: on 0337a79, a monitor that returns a fallback for an A ⇄ B cycle hides the cycle entirely. B is cached holding the fallback A, while A is cached as the real one, so the container holds two different As. Decided by the maintainer on 2026-11-09: a cycle may only become another error.
