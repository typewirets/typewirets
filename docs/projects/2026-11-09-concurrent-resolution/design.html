Core tracks chains and waits; the monitor keeps its shape

Key: concurrent-resolutionDate: 2026-11-09Author: Claude Code (Opus 5.5)Status: design brief, waiting for an approach pickSource: product.html (approved 2026-11-09), core at 0337a79, typewirego container.go

Recommended: A1. Core gives every step its own chain and checks a container-wide wait-for map before joining an in-flight creation, so cycle detection is built in. The existing monitor interface stays and gains an optional third argument carrying the step's path. Existing monitors keep compiling, and the release is 0.3.0.

Approaches: how the monitor fits

All three use M1 and M2 for detection. They differ in the monitor API.

A1. Keep the shape, add the path pick

What
monitor and monitorAsync keep their signatures, plus an optional third argument step: { path, requestId }. Core runs the cycle check inside the step's action and enforces B12 after the monitor returns. CircularDependencyMonitor becomes a pass-through and is deprecated.
Effort / risk
M / low. Existing monitors compile unchanged.
Reuses
The factory and option, the error format and getErrorMessage.

A2. A new step hook

What
One container-level onStep(step, next) middleware, with a step object (type, path, kind: cached, joined or created). The old factory stays for one release through an adapter.
Effort / risk
M–L / medium. Two APIs during deprecation, and more to document.
Gains
Step kinds and a cleaner model, but no B line needs them today.

A3. Observer only, like Go

What
Events go to a queue and the observer can't change any outcome (typewirego doc.go: "can observe but never change container state").
Effort / risk
L / high. A breaking change.
Verdict
Fails B11, which you decided: a monitor can change outcomes.

R1. Recommendation: A1

  • Delivers every B line with the smallest public change: one optional argument.
  • Keeps B11's power through the same wrapping call monitors use today, and B12 is enforced by core, not by trusting the monitor.
  • Leaves room: if anyone asks for step kinds or tracing, A2 can be added later on top of A1 without another break.

Shape

Bounds and latitude

N1Appetite: one core PR, with changelog entries for core, react and inversify. If the wait-for check (K1) grows past its timebox, stop and report.
N2No AsyncLocalStorage, no timers, no new dependencies. It must run in browsers.
N3No public type or export is removed. A monitor written for 0.2.0 compiles unchanged. CircularDependencyMonitor stays exported, marked deprecated.
N4Unchanged: the async contract of createWith, the semantics of preload, getSync's AsyncOnlyBinding, and the #28 rule that a creation from before unbind never touches the cache.
N5The React and Inversify suites pass unchanged. All three packages release together, following the MAINTAINING.md checklist.
N6Not now: step kinds or tracing events (A2), a validate() API, static checks of declared imports.
L1The builder decides alone: data structures, file layout, how an error's path is assembled within B7 and B8, internal names, and test layout.
L2The builder checks first: any public type change beyond the optional step argument; any B line it can't meet (say so, don't weaken a test); anything that would break a 0.2.0 monitor.

Claude's calls, for you to check

C1Release 0.3.0, not 0.2.1. Custom monitors change behaviour (they can't switch detection off or turn a cycle into a value), and before 1.0 a minor version is where behaviour changes go.
C2Wait-for edges point at creations, not types. A creation from before unbind and its replacement can be in flight together (#28), and keying by type would mix them up.
C3Each request caught in a cycle gets its own CircularDependency, with a path built from its own chain (B7: the path starts at the request's type). Otherwise the request that joined would receive the other request's path, such as B -> A -> [B] for a request that started at A. Every other failure of a shared creation is still one error object shared by all requesters (B2).
C4B12 is silent: if a monitor returns a value for a CircularDependency, core rethrows the original error, logs nothing, and documents this in the TSDoc.
C5A monitor that never calls action skips that step's creation, and with it the cycle check. No cycle can form through a step that creates nothing, so B9 holds for every step that runs.

Risks and rabbit holes

K1The wait-for walk must be right with nested creations, transient steps in between, and joins started from getSync paths. Timebox: 1 day, including a test that builds random small graphs, resolves them concurrently, and compares the outcome with single-request resolution.
K2Edges must not leak after creations settle, through success, failure or unbind. A test resolves a diamond graph 1,000 times concurrently and expects no error.
K3Building each request's own path (C3) for a joined cycle. Timebox: half a day. Falling back to a shared error breaks B7, so report rather than ship that.
K4React caches errors until clearErrors (#31). A cycle fixed by re-applying a wire still needs clearErrors in React, which is already documented, so no change.
