An app loads its async wires once per phase, and React components then render without waiting

Key: preloadDate: 2026-11-06Author: Claude Code (Opus 5.5), with the maintainerStatus: approved 2026-11-06Source: the maintainer's answers in chat on 2026-11-06; follows the sync-createwith decision

Async stays the wire contract. An app waits for its async wires once, at the start of each phase of its life (startup, login, a route), and from then on its components read those wires synchronously: no fallback flash, no loading waterfall. The behaviour below delivers that.

Value

  • V0. For apps built on typewirets, React apps most of all: wait for async setup once per phase instead of once per component, so screens appear complete on first render while every wire keeps the async contract and overrides stay free to be sync or async.
  • V1. One wait per phase replaces a chain of fallbacks, where each component finds its own async wire only when it renders.
  • V2. Async work happens when the app is ready for it: user-scoped wires after login, feature wires when their route loads, not all at startup.
  • V3. Setup failures surface at a point the app controls (startup, login, route entry), not inside an arbitrary component.
  • V4. Forgetting to preload a wire costs a fallback, never a broken screen.

Where preloading happens

Behaviour

GroupWhat happens
PreloadB1. An app can wait until a set of wires it names, and everything they import, has been created. Afterwards each of those singletons is returned by getInstanceSync, and every read returns the same instance.
PreloadB2. An app can instead wait until every singleton bound in the container at the time of the call has been created. No transient wire is created by this.
For small apps, servers and tests.
PreloadB3. If any creation fails, the preload rejects with that creation's own error, unchanged. No other failure in the same preload surfaces as an unhandled rejection.
PhasesB4. A later preload (after login, before a route renders) creates only what isn't created yet; wires preloaded earlier are not created again.
PhasesB5. After wires are unbound (logout) and applied again, preloading them again creates fresh instances.
ReactB6. A component that reads a preloaded wire with useTypeWire renders on its first render with no Suspense fallback, also when the wire's value is falsy (0, "", false, null).
ReactB7. A React app can preload a set of wires at a point in its tree (a route, a panel). The subtree shows one fallback until the whole set is ready, then renders without further fallbacks for those wires.
ReactB8. A component that reads a wire nobody preloaded still works: it suspends, then renders when the value arrives, as today.
LearnB9. The React README leads with preloading: startup preload before the first render, a preload at login and at a route, and when Suspense alone is fine.
LearnB10. The docs state the contract: every wire is read through getInstance; getInstanceSync reads what is already created; overrides may be sync or async.
CyclesB11. A real dependency cycle hit while a set of wires preloads in parallel raises CircularDependency instead of hanging.
