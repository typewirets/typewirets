A createWith wire with only synchronous imports is ready synchronously, on first use

Key: sync-createwithDate: 2026-11-05Author: Claude Code (Opus 5.5)Status: approved 2026-11-06Source: issue #21, PR #28 review, core at 67f6cfb

Code that reads a synchronous createWith wire gets its value at once, the first time, and React components that use it render without a loading fallback. Wires that need async work keep behaving exactly as they do today.

Value

  • V0. For apps built on typewirets, and React apps most of all: a wire that needs no async work can be read synchronously from the first read, so the sync API and useTypeWire work for it without preloading and without a flash of fallback.
  • V1. The recommended way to declare a wire (imports + createWith) stops costing a Suspense round trip.
  • V2. getInstanceSync means what it says: it fails only when something really is asynchronous.
  • V3. Nothing that works today breaks: async wires, cycle errors and "created once" all hold.

Behaviour

GroupWhat happens
Sync readB1. A createWith wire whose createWith returns a value, and whose imports are all synchronous (all the way down, including other createWith wires), returns its value from getInstanceSync / container.getSync on first use, without any earlier getInstance.
Sync readB2. Each singleton in that tree is created once, and later sync or async reads return the same instance.
ReactB3. useTypeWire on such a wire renders the component on first mount without showing the Suspense fallback, and creates it once (also under StrictMode).
Async stays asyncB4. A wire with any async import anywhere in its tree, or whose createWith returns a promise, resolves through getInstance as today. getInstanceSync throws a retriable AsyncOnlyBinding until the value is cached, then returns it.
Async stays asyncB5. Every import is created once per resolution as today, including a transient import whose creator is async (it is not run a second time to "try sync first").
ErrorsB6. A cycle through createWith wires raises CircularDependency, whether reached by a sync or an async read, and the printed resolution path names the wires in the order they were entered.
ErrorsB7. When a sync wire's createWith or a sync import throws, getInstanceSync throws that error itself (today it throws AsyncOnlyBinding and the real error surfaces later). getInstance rejects with it, as today.
UnchangedB9. apply and bind stay async and are awaited as today; getInstance and container.get always return a promise. Only a synchronous read of a fully synchronous createWith wire changes.
UpgradeB8. The changelog and docs say that a createWith wire's creator can now return a value instead of a promise, and that withCreator decorators should await (or otherwise accept a plain value from) the creator they wrap.
