Resolve createWith imports sync-first inside the core container, on top of #20's per-step chains

Key: sync-createwithDate: 2026-11-05Author: Claude Code (Opus 5.5)Status: A1 picked 2026-11-06Serves: product.html B1–B8

Recommended: A1. The container tries each import synchronously, runs it only once, and finishes asynchronously from the first import that turns out async. It needs #20's per-step resolution chain first: on today's shared cycle-detection stack, mixing sync and async reads corrupts the stack (measured below).

What the spike showed

Throwaway spike, Node 24, against core at 67f6cfb. "Naive" means: createWith reads each import with getInstanceSync, and falls back to getInstance on AsyncOnlyBinding.

  • E0. Nothing is inferred up front. Whether an import is async can't be known before it runs. A1 doesn't guess: it runs each import once and looks at the answer (a value or a promise), as the container already does for plain creator wires. At the first promise it keeps that promise and finishes the rest async. A second spike of this on current main: an all-sync tree read sync on first use, each wire created once; a tree with an async import threw retriable AsyncOnlyBinding on a sync read, then getInstance worked and the async import was created once; a transient async import was created once per getInstance.
  • Why E1: CircularDependencyMonitor.remove pops the top of a stack shared by the whole request (index.ts:865). A sync frame that ends after an async child was pushed pops the child instead of itself. #20 (P3a in the triage plan) replaces this stack with a per-step chain.
  • Why E2: getSync runs a transient creator, gets a promise, throws, and drops the promise; the fallback runs it again.
  • Inversify: the adapter's getSync throws Inversify's own error for an async binding, not AsyncOnlyBinding, so a getSync probe can't tell "async" from "broken" there.

Recommendation

R1. A1. It is the only option that gives the default React fix (V0) without weakening cycle errors (V3, B6), and the chain rework it needs is already planned for 0.2.0. A2 does the same work twice; A3 leaves #21's React symptom for everyone who doesn't opt in.

Bounds, latitude and my calls

  • N1. No new public API. The "value or pending" step stays inside the core container.
  • N2. Imports still resolve one at a time in declared order; no concurrency is added here.
  • C1. My call: contexts other than TypeWireContainer (Inversify adapter, custom ResolutionContexts) keep today's async path, because they can't say "this is async" without running it twice (E2, Inversify note). React gets the fix, because the container, not ReactResolutionContext, calls creators.
  • C2. My call: ship in 0.2.0 with #20; changelog entries in core and react.
  • L1. Builder decides alone: internal names, how the pending step hands off to async, test file layout. Checks first: anything that changes a public type or the monitor API beyond what #20 already changes.

Risks

  • K1. #20's chain design may land differently from the triage plan. A1 only needs "each step knows its own chain"; adapt to whatever lands. No A1 code before the #20 PR is up.
  • K2. withCreator decorators that call .then on the wrapped creator's result break for sync wires. Covered by the changelog (B8); Creator is already typed T | Promise<T>.
  • K3. Not now: useTypeWire tests if (value), so a wire whose value is falsy still suspends. Separate small fix.
